# 三维资产的工具分工与选择

> 2026-09-17 制定。适用当前 Windows 窗口版、江南微缩田园方向；这是制作决策基线，不代表表中资产都进入首版。安装版本、调用入口和已完成测试见 [开发准备](development-setup.md)。

执行入口为项目级 [farm-3d-asset-pipeline](../.agents/skills/farm-3d-asset-pipeline/SKILL.md)，用于资产生产、拆件动画、LOD 修复及过程素材检索；本文件继续维护详细制作规范，避免复制两份参数和流程。

正式 GLB 重导出后，先运行 Godot 导入以生成对应贴图，再运行 `python scripts/share-glb-textures.py --art Game/art --all`，最后重新导入。该脚本按实际图片 SHA-256 使重复模型引用同一张外部贴图，不重采样制作源。移除多余的 `Game/art` 提取贴图前，核对其 `.import` 参数、GLB URI 和场景／动态加载路径；`ArtSource` 原图仍保留。发行包审计会对实际包内字节核验 SHA-256，发现重复项即阻止出包，以免重导出使副本回流。

## 选择原则

**当前商业目标包含展示 Tripo 平台：在满足游戏质量与可维护性的前提下，优先用 Tripo 制作可见资产及可复用部件。** 图片生成工具负责统一参考，Tripo 负责三维候选与外观生产，Blender 负责组装、尺寸、阶段修正和必要清理，Godot 负责场景组装、玩法表现与最终验收。不要求每个资产经过所有工具。

判断顺序：先确定资产在游戏与展示中的用途，再判断完整生成或部件生成是否可控，最后比较生成、修整、导入与修改成本。普通作物、陶罐、静态建筑外观也可优先 Tripo，不再只把它用于复杂装饰。精确地块尺寸、拼接接缝和纯动态效果仍交给 Blender / Godot；低多边形不自动等于低成本或符合画风。

平台推广价值是选型依据，不是降低验收的理由。真实贡献与过程证据统一保存在仓库根 [制作留档](../制作留档/README.md)。每条对外内容至少让观众看到一次“Tripo”及它生成的具体资产或部件，并区分 GPT / Astra 的设计、提示词、代码协调，图片生成工具的出图，以及 Blender 修整和 Godot 表现。模型名以实际运行记录为准；不得把参考图或手工重建的部分宣称为 Tripo 原始输出。此规则不授权自动发布或给甲方发消息。

以下分工结合工具能力、本项目需求和商业目标。Blender 基本自动化已实测，Godot 已有简易场景与镜头原型；Tripo 青菜经 Blender 整理后已接入实际场景。该静态资产链路通过导入与初步画面检查，最终美术、代表性硬件性能及动画质量尚未验证。

## 按资产类型选择

| 类型及例子 | 首选制作方式 | 其他工具的作用与选择理由 |
|---|---|---|
| 原型体块、地块占位、交互范围 | Godot 基础几何体 | 先验证大小、构图和点选。需要正式轮廓时再换 Blender 模型，不为占位付费生成；简单体块符合最终风格时可以保留 |
| 田畦、田埂、院墙、石板路、篱笆、桥面等拼接件 | Blender | 精确控制尺寸、接缝、枢轴，复用部件；Godot 负责摆放与组合。避免分别生成相邻模块再花时间消除接缝 |
| 民居、亭棚等静态建筑外观 | Tripo 整体或部件候选 → Blender 整理 | 静态房屋可整体生成；需要开门、拼接或替换屋顶时先明确部件边界，Blender 校准结构；检查比例、江南形制和背面 |
| 作物幼苗到成熟的阶段资产 | Tripo 整株阶段或叶片部件 → Blender 对齐 / 组装 | 离散阶段切换不要求同拓扑；统一品种、根部、尺度、色彩与展开趋势。可独立生成各阶段，也可用同源叶片组装 |
| 树木、竹子、草丛、花簇 | Tripo 整体或枝叶簇 → Blender 整理复用 | 避免每根竹节都发一次请求；规则性竹竿和接缝可直接建模。风动由 Godot 实现，密集植被检查透明叠加与阴影开销 |
| 陶缸、木箱、水桶、板凳、简单农具 | Tripo 优先制作代表物件 → Blender 修整 | 简单可见道具也有平台展示价值；系列尺寸、把手连接和枢轴由 Blender 统一。不为不可见的编织细节默认生成高面数模型 |
| 不规则观赏石、盘根树桩、复杂静态摆件 | Tripo 候选 → 按需 Blender 修整 | 适合先探索整体造型，再处理底部、穿插、面数和材质。小石块或简单轮廓仍可直接 Blender 制作；生成结果不合格时比较重建成本，不无限修补 |
| 猫、鸡、人物等需要活动的角色（若纳入范围） | Tripo 外观候选或 Blender 建模 → Blender 检查与修整 | 可试 Tripo 绑定与动作，但须验证实际体型、关节变形、脚底接触和循环；Godot 配置动画播放与行为。不能把静态好看或自动绑定成功当成动画可用，也不把四足或鸟类套成人形骨架 |
| 水面、涟漪、雨、雾、烟、选中轮廓、生长提示 | Godot 材质、动画或粒子等当前所需能力 | Blender 仅按需提供水岸、石头等承载几何；不把动态效果生成成静态实体。没有需求时不提前引入复杂特效系统 |
| 整座农场与可操作场景 | Godot 用组合场景组织独立资产 | 保留作物、地块、装饰的独立身份；不生成一个难以选中、替换和保存状态的整场景网格。Tripo 场景候选只能作为造型参考 |

同一类别允许例外：简单占位直接 Godot，精确尺寸变体可基于已有 Tripo 源在 Blender 修改；固定远景建筑可接受整体模型，可开关门的近景建筑需要可控分件。合理增加 Tripo 的实际贡献，不为了统计调用数量无限拆分简单部件。

## 整株还是叶片

游戏资产交付单位是“一株作物的一个生长阶段”，当前玩法状态按六田各 4×4 小格独立保存。完整作物不等于必须只有一个网格，也不要求游戏逐叶管理。

| 路线 | 适用情况 | 当前取舍 |
|---|---|---|
| Tripo 生成整株 | 风格明确，希望快速得到完整模型；允许离散阶段切换 | 先用获选青菜图验证成熟整株。后续阶段共享品种与风格参考，可单独生成；Blender 校准根部、大小与色差 |
| Tripo 生成带叶柄的叶片 / 叶簇 | 整株输出粘连、阶段不连贯，或需要更容易控制叶片展开 | 合理的第二条路线。单体图显示厚度和叶柄连接；少量代表叶型即可，由 Blender 旋转、弯曲、缩放与组合，不逐片重复付费 |
| Blender 补形 | 简单修补、精确接地、叶柄连接或阶段比例调整 | 完善 Tripo 成果；修补接近重建时记录原因，再调整生成单位或制作方式 |

三个离散模型无需相同顶点数，也无需每片叶子一一对应。仍应保持品种不变、根部不跳位、株型总体长大、叶片展开合理及材质一致。未来需要连续网格形变时才引入对应拓扑或骨骼要求；当前不预建逐叶骨架、生长模拟或连续形变系统。

Blender 的链接复制允许不同对象共享网格而分别改变变换，可复用叶型；要独立改变叶形时再复制独立数据。此能力不代表本项目叶片已生成。[官方链接复制说明](https://docs.blender.org/manual/en/latest/scene_layout/object/editing/duplicate_linked.html)。

## Tripo 内部模型如何选

具体版本、CLI 自动选择、P2 四边面、纹理 v3.5、语义分件兼容性及官方来源集中维护在 [Tripo 能力与生成工作流](tripo-workflow.md)。每个新的生成或处理任务先读相关条目，主动比较解决当前质量问题的能力；同一任务复用已核验契约，有版本变化或新问题时定向补查，不从头重复调研。

几何复杂度、可编辑拓扑和纹理质量分别决定：复杂源形体可选 H3.1，低模结构可比较 P1 / P2，几何合格但外观欠佳时优先评估独立纹理处理。新版本、四边面、高面数或 8K 都不自动保证目标画面更好；按明确收益做代表样本，不默认全量换模型。不能因游戏运行在 Windows 就套用 `game-pc` 高预算预设，也不直接将 `game-mobile` 的预算当作项目标准。

输入方式：用户明确要求所有 Tripo 模型生成都先调用图片生成工具制作单体参考图，检查后再图转模型，包括探索候选，不直接走文字转模型。要多种形态时分别生成多张单体图，再逐张生成模型；不把多个候选拼贴成一张输入。保留实际图片、提示词、风格参考顺序与模型任务的对应关系。多视图必须表现同一物件，不能混合不同设计。不要直接将整张场景图板当成一个道具输入，也不要假定自动补出的背面符合设计。具体准备方法见下节。

## 图片驱动的制作流程

2026-09-17 更新。用户已选定 A 工笔淡彩全景 + A 淡彩青菜，固定参考与提示词入口为 [风格基准 v1](design-baseline/style-guide.md)。图像风格通过不等于三维质量或实际相机运动通过，模型证据按样本记录。

### 两类图分别做什么

| 图的用途 | 需要呈现 | 不能拿它证明什么 |
|---|---|---|
| 运行界面参考 | 单张完整游戏画面、实际拟用镜头、作物与地块大小、最少必要 HUD；用于比较构图与风格 | 不证明功能已实现、模型结构正确或实际帧率；不能作为整场景网格输入 |
| 单体建模 / 生成参考 | 一个明确物件、完整轮廓、干净背景、适合观察结构的视角；用于 Blender 设计或 Tripo 输入 | 不证明背面、底面、真实尺寸、拓扑、UV 或绑定可用 |

先选少量同构图的运行画面比较风格，再把选定参考与固定的造型、材质、色彩约束共同用于单体图。重复相同风格词可以减少漂移，但不能替代共享参考图和逐张检查。场景里的物件如果被遮挡、裁切或透视严重，应单独重新生成；不直接裁下来当作完整资产图。

对于 Tripo 候选，先锁定单体外观再生成网格，有利于在较早阶段筛掉结构和风格错误。对于规则明确的 Blender 模块，可以直接按共同风格建模，必要时从体块渲染出结构参考；不要为了遵循流程给每块田地增加一次图片和三维生成。

### 单体参考图规范

下表中的画面占比与角度是本项目的起始建议，不是 Tripo 的接口限制；实际格式、尺寸、模型能力与输入数量在调用前核对当前 CLI / 官方接口文档。

| 维度 | 起始要求与检查方式 |
|---|---|
| 内容 | 一个独立资产或一个明确设计成整体的物件；不混入手、人物、花盆旁的地板、景观底座、文字、尺寸线、UI、其他备选款式。盆栽是否连盆必须由资产用途决定 |
| 结构 | 数清支脚、把手、叶片组等关键部件；接缝、孔洞、接地面和重心可信。薄片、细杆不能在图上断裂、融合或穿插；这些错误先修图或改用建模，不寄希望于重建自动纠正 |
| 背景 | 单一中性背景，与主体轮廓有足够对比；浅色物件不要融入白底。无地面纹理、场景、底座或强投影。不要把棋盘格画进图里冒充透明背景；需要透明时先核实输入支持 |
| 视角 | 通常用弱透视的三分之四视图，同时看清正面、侧面和少量顶部；约 10°～25° 俯视作为起点。避免过高俯视压扁高度，也避免广角夸张。资产视角不必等于游戏镜头 |
| 构图 | 整个物件完整入画，四周留白；主体约占画幅 70%～85%，不得切掉底部、把手或叶尖。优先方图、清晰轮廓，起始可用约 1024 像素或更高图；以工具实际支持为准 |
| 光照与色彩 | 中性、均匀、柔和，保持材质可辨；不要戏剧性明暗、强反射、景深或厚重调色。淡接触影可接受，但明显阴影可能被重建为几何或写入贴图，须在结果中检查 |
| 风格 | 固定主参考及文字约束，匹配轮廓夸张程度、材质粗糙感、细节密度和配色。提示词里的“game-ready”不能保证游戏资产质量 |
| 多视图 | 只有隐藏结构确实重要且本次工具支持时才增加；分别提供同一物体的正、侧、背等视图，保持尺寸、部件、颜色和光照一致。不要把拼贴板当成多张输入，也不要用互相矛盾的独立生成图 |

Tripo 官方建议突出单一清晰主体、完整轮廓、简洁背景和可辨认结构；三分之四视图是有用的单图起点，多视图可补充隐藏侧的信息，但仍需检查输出。上表对游戏用途和数值的取舍是项目建议。[单图准备指南](https://www.tripo3d.ai/blog/best-images-for-image-to-3d)、[多参考图说明](https://www.tripo3d.ai/blog/multiple-reference-images-3d-generation)

不同资产的重点不能全部压成同一个提示词：

| 资产 | 图像需要特别表达 | 制作取舍 |
|---|---|---|
| 罐、桶、篮等道具 | 开口、把手连接、底部；不可只给顶视图 | Tripo 优先出代表模型，Blender 校正尺寸和连接；不可见的内部无需盲目细化 |
| 石头、树桩等不规则物件 | 整体连通关系、接地范围、主要突起，避免被读成多个物体 | 独特复杂轮廓可试 Tripo；简单石块直接建模可能更快 |
| 作物 | 确切品种、根部、叶片生长方向和阶段体积关系 | 各阶段共享参考；Tripo 可独立生成离散阶段，也可生成叶片后 Blender 组装，逐个核对株型与体量 |
| 建筑和拼接件 | 可见侧、屋顶关系、门窗位置；另用尺寸和模块约定控制接缝 | 图片只管外观，精确尺寸用建模约束；需要开关的门窗不能与主体焊死 |
| 需要活动的动物或人物 | 四肢彼此可区分、身体无遮挡、适合其物种的中性姿态 | 不一律套人形 T 姿势；须另外验证骨骼、关节变形与动作，不靠静态图验收 |

需要可靠多视图时，可先在 Blender 做低成本结构体块，再用同一体块渲染不同方向；图片生成用于风格探索。这样结构有同一来源，不让互相矛盾的正背图进入重建。

### 提示词如何组织

使用“固定风格段 + 本次物件段 + 输入画面要求”三段；当前完整模板与青菜、陶罐、民居物件段统一见 [风格基准 v1](design-baseline/style-guide.md)。以下只保留通用结构示例，实际出图应使用 v1 的工笔淡彩约束；它不是 Tripo 参数，也不保证图转模型接口接受额外文字修改：

```text
Style: a coherent stylized 3D Jiangnan miniature game asset; softly rounded
silhouette, broad readable forms, matte natural materials, restrained
celadon / moss / ivory / slate / warm-earth palette, sparse surface detail.
Use the supplied style reference for materials and shape language only.

Object: exactly one [物件、品种、部件数量与连接关系].
Its silhouette, contact area and proportions are [具体结构要求].
Include [必要部件]; exclude [本次容易混入的物体].

View: complete object, three-quarter view, weak perspective, modestly
above the object, all contours sharp, centered with a clean margin.
Plain neutral contrasting background, soft neutral diffuse light,
minimal contact shadow. No scene, pedestal, text, UI, collage,
cropped parts, extra objects, depth of field or dramatic shadows.
```

给模板填具体结构，不要不断堆“高质量、超精细、4K”形容词。正面结构已经锁定时，后续修改优先基于同一图编辑并明确只改哪一项；每次仍检查结构有没有随风格修改而漂移。当前实际完整提示词及参考关系在 [生成记录](design-baseline/generation-record.json)。

### 从好看的图到游戏资产

图像检查通过后，才为明确的三维候选提交请求。根据当前工具能力明确是否生成纹理、目标面数与模型版本；保存真实用量，不默认开启所有高清和后处理选项。

拿到模型后要检查：轮廓是否匹配、背面和底面是否合理、部件是否意外粘连；实际三角形数、UV、法线、材质槽和贴图是否合适；大小、朝向、枢轴能否正确摆放。碰撞、作物状态、交互和动画由游戏需要决定，不能假定生成模型自带。需要昼夜变化时重点检查贴图是否带有不应固定的强阴影或高光。

最终将 GLB 放入 Godot，以目标镜头、显示大小和代表性同屏数量检查。没有可见收益时不增加微小几何、贴图尺寸或材质槽；不为所有资产一律要求 LOD、重拓扑或动画。导入成功、静态预览好看、图片标注“游戏资产”，都不能替代这一步。

### 本轮得到的可复用经验

- 只比较材质风格时保持布局一致；用户需要多方向探索时，可以改变角度、内容和氛围，但应标明各图在比较什么，不当作单一变量测试。当前先以全景和点击聚焦验证构图，再定风格，不能为便于比较把用户需要的三维镜头固定住。
- 从全景图生成聚焦图仍可能改变局部植物、建筑与道具；它只能表达镜头意图，不能证明多视图几何一致。实际开发必须在同一三维场景中移动相机，检查全景可辨田块、近景可辨操作对象。参考图的细节、数量和角度不能直接当作模型或玩法事实。
- 石头首图的“三个鼓包”形成近似叠石的分缝；修订为单一连续体后才得到清楚的单物件轮廓。遇到结构歧义先修输入，修图后仍不代表隐藏面或网格已验证。
- 作物图可能把“白菜”画成圆白菜；需要明确品种和叶型。原图有多株幼苗不决定玩法状态粒度；当前按小格独立管理状态，显示株数不等于产出数量。
- 单体放大容易把温润的场景参考误译成摄影细节。用户已指出写实青菜不符预期，进一步简化应落实到宽圆叶形、减少细脉与纹理，而非只在提示词里加入“卡通”。
- 中国画探索需要把形体输入与材质笔触输入分开。水墨白色断笔可能像破洞，细线可能像几何凸起；不要把强笔触图直接当作完整几何依据。原画来源与使用记录见基准包，不能把收藏印、题跋或老画黄化一并变成游戏风格。实际相机转动时的笔触稳定性仍待验证。
- 上述图像经验来自图片生成与目视检查；三维小样的实际证据见下节，已有静态青菜的 Godot 原型截图，但未完成最终画风验收，不将单次结果推广成所有生成的保证。

## LOD 与破面验收

以下为 Godot 4.7.2 / Blender 5.2.2 的项目流程，2026-09-17 实测。LOD 制作和运行时选档是两个环节：Blender 或 Tripo 可制作较低精度几何，Godot 按屏幕误差或可见距离选档。院落近景仍保留人工高档，作物加载对应阶段标准档；邻居岛与岸边水生植物按距离切人工档，开阔水面的菱叶使用人工低档。院落许多高低档仍同时持有，不能因切换可见性就宣称释放了资源。

**本次根因与修复。** `focus_detail.gd` 曾给非选中作物、装饰和复杂环境设置 `lod_bias=0`，近距离也强制选最低自动档。现改为普通1、选中作物2；视口阈值保持1像素，移除模块特殊128偏置。镜头前景的128只保留其独立用途。荷花、岸石和桂花保留已检查的显式资源；2026-09-24为房屋、岛屿、厨房、灯笼、萝卜串及院落竹／菊／苗的高档启用自动LOD，人工低档和动物蒙皮不叠加自动减面。没有全局关闭LOD，也没有修改生成原件。官方说明见[Godot mesh LOD](https://docs.godotengine.org/en/4.7/tutorials/3d/mesh_lod.html)。

**“碎面”不都等于真实破洞。** 区分薄叶轮廓塌陷、独立小部件消失、单面背剔除、法线／UV接缝、共面闪烁和实际开口。依次关闭风动、换不透明双面灰材质、显示线框、对比原始／导出／自动各档，再确定修哪里。拓扑统计用审计副本按位置焊合UV／材质接缝；不能把导出拆点都算破洞，也不能把设计上的开口一律填上。三角面本身合法；四边面导出渲染仍需三角化，四边面、面数大或P2名称都不保证LOD完整。

Godot当前[导入器源码](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/resources/3d/importer_mesh.cpp)按材质表面处理、锁几何边界、保留部分属性误差，但允许裁掉小独立组件；骨骼／形态键会进入变形处理，任意自定义风动着色器不自动等于骨骼变形。因而错误选档可产生明显缺件而不增加开边。47件正式模型本轮对照中，自动最低档没有比基础档增加开边；这不证明所有姿态／资产永不自交或撕裂。桂花原件闭合，语义分割后的1514条开边属于切口；游戏使用原整树和连续权重，没有把19个切口部件直接旋转。

本次另外定位并修复桂花人工低档的独立问题：GLB导入为UV接缝拆点，直接Decimate会分别移动几何边界。失败低档22114三角、按位置焊合审计后仍有9342条开边（总长约570.84米）；高档0开边，证明破口来自本地处理，不是Tripo原件。现仅在低档工作副本先焊合真正重合的几何接缝、保留面角UV，再减面、重新导出并审计；不对原件破坏性焊合，也不误合并本应分开的接触薄片。闭合母版→人工低档及基础档→自动LOD都纳入闭合性回归。Blender源阶段检查与Godot重导入检查必须同时覆盖，不能只检查基础高模。

| 路线 | 本项目使用条件与限制 |
|---|---|
| Godot 自动 LOD | 普通静态／低风险资产，正常屏幕误差选档；检查各档实际轮廓和贴图，开关本身不是质量保证。适合已通过验收的模型，不能靠零偏置强制省面 |
| Blender 检查过的人工档 | 近景主资产、薄叶细枝、屋檐窗格、会变形的树木优先。保留母版；按部位保护轮廓和连接、制作适度低档，检查法线／UV／权重，再由Godot选档。[Decimate](https://docs.blender.org/manual/ja/latest/modeling/modifiers/generate/decimate.html)有顶点组控制；Planar的UV／接缝保护不能误称为所有模式通用。只换成统一比例Decimate不会自动更好 |
| Tripo v2智能重拓扑 | 高模需要重新组织拓扑时的小样候选，支持目标面数、可选四边面、贴图烘焙和指定分件；是制作步骤，不是运行时LOD系统。见[当前接口](https://developers.tripo3d.ai/en/docs/mesh-decimate)。更改拓扑后须复核UV／蒙皮／风动权重，不能假定继承；本次没有调用该付费路线 |
| 自定义meshoptimizer／植被专用LOD | [meshoptimizer](https://meshoptimizer.org/)支持属性误差与边界控制；只有现有工具确有不足才接入。大量远景树可评估叶簇／广告牌或[HLOD](https://docs.godotengine.org/en/4.7/tutorials/3d/visibility_ranges.html)，会影响透明排序、阴影与自由视角，当前小院不引入新依赖或广告牌 |

每次制作执行：①保留参考、原件和未减面导出；②先定位是否选档错误；③按同机位、同灯光、同显示尺寸比较基础档与候选档，比较算法时统一预算；④正背侧检查叶缘、茎、孔洞、贴图和材质接缝，动态资产检查根部、接口、摆幅与裁剪范围；⑤检查全景／聚焦／自由近看／远离再返回、标准／低画质及新实例；⑥记录源三角数、各档数与实际绘制量，性能采样注明分辨率和前后台。被否定的档不用作正式近景，不为凑目标面数继续强减。

复核入口：`tests/mesh_lod_test.gd -- --output=<仓库.local下绝对目录>` 枚举正式GLB，输出基础／最低拓扑、真实近远绘制数与近景图，验证靠近恢复和闭合源不新增开口；`tests/focus_detail_test.gd -- --functional-only --output=<隔离目录>` 检查实际农场的选中、取消、重建与画质切换，不抢焦点，其计时不作性能结论；`tests/osmanthus_debug_scene_test.gd` 检查真实场景没有零偏置及自由视角。自动计数不能取代实景目视与动画录制。

## 工具之间怎样交接

本节是后续资产生产必须遵循的完整顺序。Tripo 生成必须经过图片工具参考阶段；Blender 精确模块和 Godot 动态效果仍按前述工具分工处理。处理项按实际需求选择，未执行的步骤如实记录，不为了流程齐全增加付费任务或要求用户逐步确认。

| 阶段 | 必须做什么 | 交接依据与记录 |
|---|---|---|
| 1. 用途与参考图 | 明确游戏中的用途、近景大小、同屏数量、尺寸／拼接／动画／阶段要求。按固定风格参考调用图片工具，先检查完整轮廓、结构和画风；多种造型分别生成多张单体图，同一物件的多视图必须一致 | 保存实际提示词、风格输入顺序、原图及采用／未采用状态；把每张选用图对应到后续模型任务，不以整张农场图代替单体参考 |
| 2. 选择生成路线 | 先读 Tripo 文档相关条目，再按问题分别选择几何模型、纹理模型和必要后处理；说明为什么选择该组合。核对本次接口支持，显式指定关键模型及质量参数，避免 CLI 自动换路线 | 按[已验证路线](tripo-workflow.md#本项目已验证的生产路线)选择起点；记录精确版本、面数预算、纹理档位、PBR、delight、种子及相关开关，区分请求值、工具默认和服务回显 |
| 3. 图生模型与原件保存 | 参考图检查通过才提交图生／多视图生成。检查真实任务状态，下载原始模型与预览；检查轮廓、背底、粘连和缺件。失败或状态不明先查原任务，再决定重试 | 原始文件不可变，保存任务 ID、输入图映射、参数、实际费用和结果。候选失败或未采用也保留原因，不用修整版覆盖原件，不把付费成功当作质量通过 |
| 4. 必要后处理与 Blender 整理 | 几何不合格先改善输入或重生成；几何合格但外观不足时评估重贴图。需要可编辑部件才分割／补全，需要拓扑或动画才重拓扑／绑定。Blender 校准尺度、轴向和枢轴，检查清理、法线、UV、材质；按镜头和同屏数量决定同源减面、高低档、贴图缩放或图集 | 按实际先后记录每一步输入／输出、工具版本、云端子任务、操作参数与改动原因；注明非等比整形、手工补形及原始／最终尺寸、三角数、贴图大小。保留可编辑源和必要重建脚本，重导入导出物复核，不能只验脚本退出码 |
| 5. Godot 正式接入 | 导出当前需要的 GLB，保留 `.import`。用场景或现有代码组合模型、材质及必要碰撞；检查新模型确实被引用，重导入后没有退回旧资源。复用变体时组合不同形状、旋转、尺寸和埋深 | 记录正式资源路径、场景／节点或实例化代码入口、比例／朝向、材质、LOD 和组合策略；新增岸石按当前水岸接口纳入距离场。检查实际运行中的高低档，不能用自动 LOD 造成的损坏判断源模型失败 |
| 6. 实景验证与修正 | 固定目标镜头和光照做前后对照，检查全景、聚焦、至少两个相反侧向近景及相关昼夜。检查相邻部件穿模、悬空、接缝和点选遮挡；动态物体检查运动范围。按风险跑相关回归及代表性同屏性能采样 | 保存实际截图、测试结果、发现的问题和修复；需要时用网格求交或运动包围区域确认穿模，再复看画面。单体预览、一次采样或编译通过不能代替组合场景验收；区分作者判断、用户反馈和未验证范围 |
| 7. 留档与交付 | 在本次制作单元结束前补齐下节记录。参考图、原模、整理源、游戏资源及证据可相互追溯；重要接入节点按测试规则录短片。完成后按测试规则用统一入口自动重启最新游戏，静音、第二屏真正全屏并保持运行；仅文档变更可保留已确认的最新全屏实例 | 更新该资产 README 的当前采用版本及重建入口，标明旧入口会不会覆盖新资源。记录成片对应提交、真实工具贡献与采用状态；完成 Git 约定，不能把本地提交或离线录制说成远端同步或实时性能通过 |

导出边界：`.blend` 留在 `ArtSource/`，游戏优先使用显式 GLB / glTF 2.0，不直接依赖本机 Blender 转换。四边面制作拓扑保留在原始 FBX／Blender 源，不能认为游戏 GLB 保留了四边面；普通 GLB 不因接入 Godot 额外付费转 FBX。程序材质、修改器、骨架与动画按实际导出物验证。[官方格式说明](https://docs.godotengine.org/en/4.7/tutorials/assets_pipeline/importing_3d_scenes/available_formats.html)

模型尺寸以可核对的尺度参照统一，采用 Godot 3D 的米制尺度约定；导出与导入后核对实际包围盒、轴向和摆放。[3D 入门](https://docs.godotengine.org/en/4.7/tutorials/3d/introduction_to_3d.html)。道具通常以接地位置作为摆放枢轴，门以铰链、模块以约定连接点为准，不对所有模型机械套用“底部中心”。具体格子大小由玩法决定。

统计统一看最终导入网格的三角形数，区分 Blender 多边形数、生成服务参数和 Godot 实际结果；同时记录有影响的材质槽、贴图尺寸、骨骼与同屏数量。先做可辨认的轮廓和温润材质，再决定微小细节；不预设所有资产都要 LOD、4K 贴图或完整 PBR 贴图组。

2026-09-18青菜复核：旧测试的3600三角上限没有性能推导，不能反过来要求新模型减至3400。先保留原模作为高档质量基准，按相同显示条件比较候选档与满田耗时，再形成资产约束；测试应验证实际契约。当前P2工笔小样保留12552三角，本机384株4K短样本未显示强减必要，详见[青菜记录](../ArtSource/Crops/Greens/README.md)。风格偏离还要检查运行材质是否叠加旧调色；不能把“保留了贴图引用”当作保留了原图设色。本次仅成熟青菜绕过增绿／压暗，绘画参考的delight开关按笔触效果判断，不默认去光照必然更好。

## 什么时候测试，什么时候请用户判断

2026-09-17 已完成首个真实 Tripo 小样：用户确认的淡彩青菜图 → v3.1 智能低面数整株生成 → Blender 5.2.2 导入与两侧渲染；一次调用消耗 40 积分，没有付费后处理或重生成。图片生成和三维生成分别留档，不能混为同一步。

该样本请求 `face_limit=6000`，实际导入 **8790 三角形**，超过试验阈值；技能中的上限说法不能替代实际统计。1 个网格、1 个材质、1 张内嵌 2048² 颜色纹理，UV 存在且无缺失文件。原始网格的接缝顶点在内存副本合并后非流形统计归零，不能把导入时的边界统计直接当成破洞。原始文件保持不变；整理版经 Blender 合并重合点、减到 2988 三角形、约 0.48 米宽、根部接地，已导入 `Game/art/crops/greens/greens_mature.glb`。六田现在由真实农场状态驱动；完整阶段与环境仍在制作。源文件、处理脚本与贡献记录见 `ArtSource/Crops/Greens/`。

1.2 代表资产已在 Godot 4.7.2 实机校对：成熟青菜及新民居通过全景、聚焦、背面、微调与夜景的开发侧视觉检查，完整院落和性能留后续任务。民居请求 18000、实际 20961 三角形，同源低档6499；详见 [民居说明](../ArtSource/Environment/House/README.md)。青菜低档曾在 GLB 重导入后直接减至1015面出现碎边，先合接缝重合点、减至1494面、清理自定义法线并平滑后改善。薄叶必须比较实际高低画面，不为追求统一减面比例牺牲轮廓；减面后还需清除退化面并以重新导入的 GLB 统计。独立样片保留在 `Game/scenes/style_sample/`，九张检查图和28秒阶段影片存于中文制作留档。

当具体资产出现选择疑问时，用一个代表性小样回答一个问题。例如“Tripo 的盘根树桩是否比 Blender 直接制作更省修整时间”，应记录实际积分、处理耗时、修整量与 Godot 画面，而非只比较生成速度。本项目现已授权资产生成与合理处理，无新总额度上限；按明确质量问题选择对象和调用，记录实际费用与采用结果，不重复索权，也不盲目批量或无限同参数重生成。参数不匹配或任务状态不明时先查原任务，避免重复扣费。

用户明确希望合理增加 Tripo 的实际参与。成熟青菜与民居代表链路已验证，后续按任务依赖扩展作物阶段与环境资产；只有出现具体质量缺口时再比较整株模型或叶片路线，样片结论不替代每个新资产的检查。

目标画风已固定；当前用户要求全程自主执行，开发侧在同一 Godot 镜头、光照和尺寸下对照参考，检查轮廓、温润材质、笔触密度和江南微缩构图，修复差距后继续批量制作。保留真实样片及开发侧判断，不把它冒称用户反馈，工具官网预览不能替代引擎检查。用户最新要求暂缓商务授权调查，保留既定参考与已有来源，不因此更换参考或重生成合格素材；不得将暂缓核验表述为商用权利已通过。

当前无需用户先决定技术参数。Godot 体块验证构图与点选；Tripo 生成代表作物，Blender 完成必要整理与精确地块，进入引擎验收后扩展同风格资产。该顺序不预先批准装饰数量或动物系统。

## 本地制作留档

用户要求仓库根的 `制作留档/` 全目录加入 Git 忽略，只存本地；它不影响正式风格图、模型和规则的版本管理，也不是运行依赖。后续每个实际制作单元结束时集中补记，无需实时抄录每条工具输出。

每件采用资产在已有 `ArtSource/<类别>/<资产>/` 下保留可追溯记录，系列资产允许一份记录按变体逐项列出。复用已有 `generation-record.json`／`task.json`、`prepare.py`、`asset-audit.json` 和 README 等结构，不另建平行台账；文件名可沿用现状，但下列内容不得省略：

| 记录内容 | 最低要求 |
|---|---|
| 参考与候选关系 | 图片工具、实际提示词、输入图及顺序、生成图文件、选择结论；工具返回的模型／种子／价格照实记录，未返回则明确标注，不反推编造 |
| 模型与调用 | 几何模型与纹理模型分别写精确版本及选择理由；请求类型、关键参数、实际服务回显、任务 ID、输入图／上一步任务、原始输出、状态、费用及失败／弃用原因。后处理云任务逐步保留关联 |
| 实际处理链 | 按执行顺序写工具与版本、每步输入／输出、清理／变换／减面／UV／材质／导出等实际操作及关键参数，注明跳过原因或未执行状态；给出现役重建命令或可执行的手工步骤及会覆盖哪些文件 |
| 最终接入与验证 | 源文件、游戏资源和场景入口，实际三角数／尺寸／材质槽／贴图、LOD 和组合策略；测试及画面证据路径、修复与限制、采用状态及用户是否确认 |

必要原图、原模、整理源、重建入口和可复用参数随正式资产管理；详细截图、排错日志、剪辑报告与视频归入下面的中文制作留档。后续代理先读资产 README 与上述记录，不凭聊天记忆复原参数，不因本地视频缺失而重复生成模型。

- 图片阶段：保存实际提示词、输入参考、生成图、当前选择状态；历史提示词缺失就标缺失，不从成图反编后冒称原文。
- 三维阶段：保存 Tripo 输入文件、任务 ID、模型版本、实际参数、原始模型与预览、实际积分及耗时；签名下载链接、凭据和账号日志不入报告。
- 处理阶段：记录 Blender / Godot 的实际操作、处理后文件与预览、检查结论；没执行的步骤写待做。
- 最终落点：记录正式源资产、引擎资源和场景位置；尚未采用的模型写“小样，未进入游戏”，不填一个未来路径冒充完成。
- 宣传素材：每条内容明确出现“Tripo”名称和具体贡献，提供可对应模型 / 部件的画面或字幕；区分对话协作、图像生成、三维生成与后期处理。仅存档不自动发布。
- 关键变化的场景短片（区分离线演示与实时操作）使用 `scripts/record.ps1` 记录到 `制作留档/05_开发录屏/`。按编号回溯制作过程，剪辑可先展示最新完成成果。每条附中文节点、镜头说明、版本与实际工具贡献；节奏和选点统一遵循 [关键节点录屏](../rules/testing.md#关键节点录屏)，不逐次录测试。

正式文档保留可跨机器复用的流程与验证摘要，详细本地留档缺失不阻塞开发。该目录不随 Git 备份，后续制作视频需使用本机副本或由用户另行备份。

重大制作节点在资产 README 中建立可检索入口，记录节点名／日期、代码基线，以及“参考图→原始模型及转角→分件展示→整理／动画→实景”的素材位置和状态；区分已有图片／视频、已有源待补拍及缺失。详细报告和录像继续使用本地剪辑／录屏索引，不复制大文件。修复前证据保留原始状态；后续从源文件补渲染须标明重现，不冒充历史录屏。桂花示例见 [20260917-osmanthus-lod](../ArtSource/Environment/Trees/README.md#视频节点20260917-osmanthus-lod)。

## 能力依据与维护

- Blender 修改器支持非破坏性几何处理，也可用 Geometry Nodes 定义修改器；这支持可重复编辑的制作方式，但不证明某个自动生成脚本的美术质量。[Blender 修改器说明](https://docs.blender.org/manual/en/latest/modeling/modifiers/introduction.html)
- Godot 场景可实例化为独立节点树，用于组合模型、交互与行为。[场景组织](https://docs.godotengine.org/en/4.7/tutorials/best_practices/scene_organization.html)
- Tripo 插件与 CLI 提供生成及后处理工作流；本文的 P1 / v3.1 / P2 适用判断结合本机技能说明，不是官方对本项目资产效果的保证。[Tripo 插件说明](https://developers.tripo3d.ai/en/docs/codex-plugin)

首次实际资产链路通过或失败后，直接修订这里的选择依据与未验证边界；通用调用、版本和排错经验维护在开发准备文档，避免复制两份环境清单。

## 常驻资源预算与静态烘焙

2026-09-24低耗优化只修改运行导入策略，保留 `ArtSource/` 及原始图像／GLB。三维彩色贴图使用BC7显存压缩和mipmap；道具、岛屿、院落小物通常1024，主体／作物2048。灯笼8K原图仅作原件，运行时上限1024。UI沿用自身图标导入尺寸，三维分辨率上限不降低UI输出清晰度。高低档继续共享纹理、网格与兼容材质。新贴图不是一律放大到预算上限；近景有可辨收益才例外保留4096。

默认岸线采样、水岸距离图和96格松土网格由 `scripts/bake-wallpaper-data.gd` 生成，正式资源为 `Game/art/environment/islets/shorelines.tres`、`default_water.res` 与 `Game/art/environment/soil/patches.res`，`.res` 走Git LFS。使用固定4.7.2引擎执行 `--headless --path Game --script ../scripts/bake-wallpaper-data.gd`；更改默认布局、相关岛屿或松土生成器时同步重建。自定义布局仍按原算法生成，不复用不匹配的默认水岸图。接触阴影采样512，松土保留原高度函数与根部接触，减少不可辨的独立颗粒。

常驻权威状态是农场、布局和摆件拥有者；活跃场景持有需要的网格／材质／纹理。`CourtyardAssets` 仅保留有限目录的PackedScene／材质缓存，长期后台清除此缓存，活跃实例的引用仍保留；这不是完整资产流送。根视口置零释放可重建缓冲，但不删除农场状态。长期后台350MiB内存／256MiB图形资源仍是验收目标，不能以这一实现替代测量。初始定位预算：可见150万三角、阴影200万、400绘制调用，当前尚未全部达到。
