## 一、交付定义与定稿边界

交付目标是一个真实可用的 Windows 单机农场游戏及可提交的发行材料，而不是仅有镜头的样片。玩家应能够理解当前状态、完成操作、退出并安全返回，有少量持续目标，且无需安装 Godot、Blender、Tripo 或开发环境。制作与推广所需的素材、贡献归因同时可追溯。

已确定：Godot、Windows 普通窗口、现实时间生长、三维全景与田块聚焦、工笔淡彩的圆润卡通形体、本地数据、Tripo 合理优先。用户指定本目录主界面参考图为最终运行界面的主要还原依据，不能只做到颜色或题材相似。2026-09-17 用户明确授权整个计划自主执行、逐项子代理交接且无需提问；1.1 据此采用下表作为制作定稿。数量、数值及发行包形式属于开发侧自主选择，不冒充用户逐项选定，且尚不代表已实现。

| 内容 | 定稿交付 | 执行边界 |
|---|---|---|
| 主界面整体效果 | 还原参考中的斜向观察距离、民居与菜田布局、水岸／石桥／木船、远山层次、工笔淡彩与简洁界面 | 视觉目标已确定；具体几何、背景与材质实现由 1.2／3.2 验证 |

### 1.1 时间、验收与发行契约

- 时间使用 UTC 秒，系统本地时钟只控制昼夜。关闭、后台、失焦、休眠均继续生长；离线最多推进当前一轮至成熟，无自动收获、多轮收益或惩罚。回拨有效增量为零并保留较新结算基准，追上后继续；前跳即使数年也只成熟本轮。集中时钟入口可注入测试时间，不改系统时钟。动作、保存与恢复遵循农场模拟规则。
- 1.1 现场可取得设备：Windows 10 专业版 `10.0.19045`、Ryzen 9 5900X、约 64 GB RAM、RTX 4090（2026-09-17 CIM 只读核验）。此为开发验收机，不是最低配置声明。4.2 记录实际驱动、窗口尺寸、画质、前后台、CPU／GPU 帧时间与工作集；其他设备和 Windows 版本未验证，不伪造覆盖。
- 性能制作目标：该机 1920×1080、标准画质、六田最大同屏、白天／夜间、全景／聚焦／布置各预热后采样不少于 60 秒，目标 60 fps，帧间隔 p95 ≤ 20 ms、p99 ≤ 33.4 ms；分别记录主线程与 GPU 数据，无法取得的指标明确缺项。首次独立启动到可交互 ≤ 10 秒，持续运行 30 分钟无崩溃、严重错误或持续内存增长，工作集 ≤ 2 GB。后台静音且降至不超过 15 fps，不暂停生长；记录真实资源变化，低帧率本身不证明低开销。4K60 仅是录制规格。
- 1280×720 为逻辑界面起点，960×600、1920×1080 与本机 4K／150% DPI 检查不裁切与中文可读；4K 不承诺同等实时性能。未有低配设备时不宣布最低配置，5.2 仍需移出仓库的隔离包／用户目录验证，不能把同一开发机冒称另一台无依赖设备。
- 视觉由执行者在真实引擎中按固定参考对照、修复并自主验收，再继续依赖任务；保留全景、聚焦、日夜对照及差距，明确是开发侧观察。院落、桥、船、水岸、远山和植被需成为实际成品景物，不能以简单色块完成全景验收，也不能将未达到的目标改写为通过。用户反馈尚未取得，不伪造用户认可，不因等待审美回复暂停。
- 用户最新第 7 条要求暂缓商务授权调查：5.1 商业核验暂停，不阻塞制作与本地包交付；保留已有来源和随包许可，不宣称商用权利已核验。特定商店材料本轮不适用，保留渠道待定事实。5.3 由执行者完成真实程序试玩并交付用户可试玩包，注明尚无用户签收。实际上架、商店付款与签名付费仍须具有对象与范围明确的授权，本次无需为这些非交付范围事项提问。

暂不纳入桌面宿主、托盘与开机启动、移动端或网页、账号联网、云存档、多存档槽、交易经济、动物角色、自由划地／建造、季节天气玩法、强制打卡或离线惩罚。计划不自动启动新订阅、上传商店、公开仓库或购买发行服务。

## 四、实施策略与状态边界

### 玩法与存档

1. 在 `Game/` 内按需要增加农场状态、作物定义和存储职责；先复用现有场景，不搭建联网后端、通用框架或全局事件系统。
2. 整田状态为权威：稳定田块标识、作物标识、累计有效生长秒数、UTC 结算基准、本轮浇水标记；累计收获、解锁和装饰位置属于农场。具体字段在 2.1／2.3 定义，只维护一处。
3. 作物静态定义与玩家状态分开；植物实例从田块状态重建。田块数量不决定收益，植株数量不等于收获篮数；相机和动画不能改变数据。
4. 时间入口可注入。先按旧状态结算到动作时刻，再处理浇水或收获；不靠渲染帧累计生长。回拨不负生长、不降低结算基准；前跳最多成熟一轮，不自动收获；离线不逐帧重放。
5. 单份本地版本化存档，建议结构化 JSON 与临时写入／安全替换／上一有效副本；这是实施建议，具体库函数与 Windows 行为须先核验。缺档、坏档、不支持版本、写入失败分别处理，不静默重置。
6. 成功动作及时保存；若内存变更尚未落盘，界面明确未保存并可重试，不提示成功保存，也不因重试重复发奖。首次初始化原子完成，存档恢复不再发首轮成熟作物。
7. 单一农事工具选择；全景点击只聚焦、换田只换目标、过渡时不执行农事、右键／Esc 取消、界面拦截、失焦释放。布置与农事互斥，取消布置不改旧位置。

### 新旧实现兼容

现有场地与相机继续运行。2.2 将成熟株的硬编码填充切为由状态生成，2.3 才启用持久化，3.3 接入完整内容；各次提交都能运行对应切片。现有用户没有正式游戏存档，不虚构旧档迁移；一旦 2.3 建立版本，后续字段变化须保存旧样例并验证迁移。不能把数组排序、节点路径或生成任务编号当玩家数据标识。

现有青菜处理脚本会覆盖整理版及正式 GLB，只在核对源文件、保存当前编辑结果后运行。新模型优先另存候选与源文件，再切换正式引用；保留 `.uid`、`.import` 与 LFS 对象，不手改 `.godot/` 缓存。模型外建立组合场景，不向原始 Tripo 文件写入玩法脚本。

| 项目 | 当前建议 | 后续调整依据 |

### 生成后的检查与处理边界

- **每个 Tripo 模型都检查**轮廓、正背底面、贴图、尺寸、接地点、实际三角形和材质；下载成功不代表可交付。
- **Blender 按需处理**：修穿插与法线、补连接、统一尺度／枢轴、组合叶片或建筑、必要减面和材质整理，再保存可编辑源并导出 GLB。已完全合格的 GLB 可以直接进入 Godot，记录“未做 Blender 编辑”，不强制重拓扑或重新烘焙。
- **所有采用模型都进 Godot 验收**：导入设置、材质／阴影、必要碰撞与点选、实例组织、阶段映射和摆放；检查全景、聚焦、转动、昼夜及实际同屏成本。LOD 已纳入本次需求，按下节落实；合图等其他处理仍按实际问题决定。
- **修正位置跟随问题**：源形体或连接问题回 Blender／Tripo 输入，实机光照和交互问题在 Godot 处理；不把烘在颜色纹理里的硬阴影误认为调灯就能消除。

### 全景与聚焦的细节分级和景深

用户已明确要求这项能力；先保证下列三种状态，具体三角形数、LOD 层级数量、屏幕阈值、焦点清晰带和虚化强度在 1.2 试样、3.5 接入时确定，不预设所有资产同一减面比例。

| 观察状态 | 模型细节策略 | 景深与可读性 |
|---|---|---|
| 全景 | 田块作物与重复环境优先使用低细节，保留整体轮廓、作物阶段和笔触色块 | 农场整体清晰可选；景深关闭或很轻，保持指定主界面的观感 |
| 聚焦田 | 使用近景高质量运行网格，保持叶型、边缘和关键结构；随缩放适配屏幕占比 | 整块操作田及作物高度处在清晰带内，界面和当前摆放目标不虚化 |
| 视图内非焦点区域 | 即使随镜头被放大，也按田块身份采用较低细节；非常靠近镜头的轮廓保留最低可接受质量 | 前后景温和虚化，旁边田仍可辨认、可切换；不靠强模糊掩盖破面 |

1. **同源制作**：Tripo 优先生成一份合格主模型；近景使用整理后的高质量运行版，低细节由 Godot 导入自动生成或 Blender 从同源减面。轮廓复杂、自动简化破坏薄叶的资产再手工制作低细节；需要验证平台减面效果时可用 Tripo 后处理，但不为每档 LOD 重新图生不同形状。各档统一根部、外形、阶段身份和材质；简单几何可共用一档，不强制把所有物件做成多个文件。
2. **焦点控制**：优先验证 Godot 自动网格 LOD，加每个田块／实例的 `GeometryInstance3D.lod_bias` 调整，不能只用全局距离阈值。偏置不能可靠满足近景和非焦点要求时，才对相关资产显式切换同源高低网格。若采用 MultiMesh，按田块及阶段组织可独立控制的节点，不把全农场混进同一组。[自动 LOD 与 MultiMesh 边界](https://docs.godotengine.org/en/4.7/tutorials/3d/mesh_lod.html)、[实例细节偏置](https://docs.godotengine.org/en/4.7/classes/class_geometryinstance3d.html#class-geometryinstance3d-property-lod-bias)
3. **切换稳定**：在镜头靠近前准备目标细节；焦点切换、返回、缩放临界点和中途取消要恢复正确状态，不沿用过期目标。按实际画面调整阈值、迟滞或短过渡，检查轮廓跳变、重影和首次加载卡顿，不假定自动 LOD 自带无痕淡化。生长阶段与 LOD 分开，固定田块碰撞／点选不随视觉网格切换。
4. **景深实现**：当前 Forward+ 下优先使用 Camera3D 的 `CameraAttributesPractical`，随目标田深度范围平滑调整清晰带与近远模糊。原生景深按深度工作，并不按田块身份遮罩；同深度旁田可能仍清楚，其降面由焦点 LOD 独立完成。低画质可减弱或关闭景深，LOD 照常工作，不把虚化当成降渲染成本。[景深参数与渲染器限制](https://docs.godotengine.org/en/4.7/classes/class_cameraattributespractical.html)
5. **交付与检查**：1.2 验证代表高低细节和景深观感，3.1／3.2 交付可用网格与导入约定，3.5 实现焦点控制与景深，4.1 接入已有画质设置，4.2 分别比较全高细节、仅 LOD、LOD 加景深的相同场景。记录实际绘制图元、帧时间和画面，不能只看 FPS 标签或用离线影片证明性能。

首次只需验证高／低两端，过渡画面需要时再增加中档。LOD 不自动解决材质、透明叶片、阴影或纹理开销；4K 下选择的细节与景深成本也需实测。高质量运行版不等于未经整理的高面数原始生成物。

### 单个资产的执行顺序

每个正式资产按同一条短流程执行，证据跟随资产，不另建庞大管理系统：

1. **说明用途**：资产名称、整件或部件、场景位置、预计同屏数量、可见面、交互与阶段、尺度和枢轴。依据游戏镜头给出本资产预算，2988 三角形只是旧青菜单样，不能变成全局上限。
2. **生成输入图**：读取固定全景与青菜，复用固定风格段，补具体物件和结构；单物体、弱透视三分之四视角、完整轮廓、干净有对比的背景、中性柔光，无界面、文字、底座或强投影。只有隐藏结构确需补充时做一致多视图。
3. **先检查图**：品种、叶片／把手／屋顶连接、底面、留白和画风。旧 `images/structure/` 图仅供结构参考，未证明符合最终质感，不直接全部提交生成。修改优先修具体缺陷，始终保留固定风格输入。
4. **Tripo 生成**：查看当前插件／CLI 帮助与官方说明，按目标选择模型、纹理和面数；若自动选择不适用再显式指定。优先需要的 GLB，避免附带无用 FBX 转换或所有高清选项。保存任务编号、输入图、真实参数、模型版本、原始 GLB、预览、耗时与费用；状态不明先查原任务，不能重复提交碰运气。
5. **检查与按需 Blender 整理**：保留原始输出，检查正背底面、实际三角形、UV、法线、材质与贴图；确有问题再修重复点、穿插、比例和接地枢轴，按实际收益减面／烘焙。叶片有意开放的边不机械判错；不为静态作物强制绑定或逐叶骨架。
6. **显式导出与引擎验收**：可编辑源存 `ArtSource/`，GLB／贴图存 `Game/art/`，组合场景放 `Game/scenes/`；全景、聚焦、小幅转动、阶段切换、日夜和代表性同屏数量都检查。单图好看与导入成功不是最终通过。
7. **接入与留档**：确认来源和采用状态后替换正式引用。必要参数与来源随正式源资产入 Git；将提示词、参考图、原模型、处理证据、最终路径各留一份到中文 `制作留档/`，未采用写明原因。签名下载链接和凭据不进文档。
8. **规模化条件**：1.2 的真实场景风格通过后才扩展成组资产；常规变体按已定标准制作，不逐叶请求审美审批。整体方向偏离时按固定参考修复并如实记录差距，由主代理协调，不等待用户回复或降低目标。

每条对外内容至少一次明确出现 **Tripo 名称与具体生成资产／部件**；同时区分图片工具、GPT／Astra 对话与代码、Blender 整理、Godot 运行。没有实际生成的部件不能记给 Tripo。宣传归因不自动变成游戏界面广告。

## 六、阶段关系与质量检查点

| 检查点 | 可观察结果 | 通过后推进 |
|---|---|---|
| 1.1 范围明确 | 内容、节奏、平台与验收有清楚口径；未知事项有解决人和截止任务 | 1.2 资产样片与 2.1 玩法核心可独立推进；5.1 商务核验暂缓 |
| 1.2 风格样片 | 代表田块、青菜与民居部件达到固定风格，低成本全景布局接近指定主界面的大关系，确认扩展路线 | 3.1／3.2 可并行制作，避免先生成整套错误资产 |
| 2.3 可保存切片 | 一种作物可种、浇、收、退出、读档和离线成熟，错误不毁档 | 接入 3.3 完整数量与解锁，不再停留在演示态 |
| 3.5 焦点细节 | 全景与非焦点区域使用合适低细节，聚焦田清晰，景深和切换不影响操作 | 4.1 接画质设置，4.2 验证完整场景质量与性能 |
| 4.2 成品质量 | 完整玩法、窗口、恢复、目标硬件与真实帧时间有证据 | 5.2 构建稳定候选；4.3 同期整理展示素材 |
| 5.3 交付 | 开发侧真实程序试玩与参考对照通过、包隔离运行、通用发行材料完整、用户签收状态与已知问题明确 | 可交给甲方或执行另行获准的实际发布 |

阶段不是强制流水线：5.1 商务核验按用户最新要求暂缓；已有来源和真实工具贡献保留，后续不因此暂停资产制作或本地出包。并行仅限读写范围独立的任务；场景整合由 3.3 负责，资源制作者先交独立组合场景，避免同时修改主场景或同一个 `.blend`。本次逐项使用子代理；完成后写 handoffs/编号-handoff.md，主代理统一协调集成和共享文档。

## 七、风险、回退与最终验收

- **范围与节奏**：首版数量与慢生长数值已由 1.1 采用，体验仍须实际验证。用首次成熟田、可控时间测试和真实等待体验验证，不在正式版本默认开启测试加速。
- **风格漂移**：只在代表样片阶段收敛一次；保留固定参考和源文件。失败候选不覆盖正式资产，有证据表明局部修整更合适时停止盲目再生成。
- **数据风险**：存档测试隔离，不调整系统时钟，不覆盖真实玩家数据。坏档、写入中断和较新版本保留原文件；数据迁移单独测试，代码回退不自动回退玩家进度。
- **性能与录制**：开发机 RTX 4090 不能代表最低配置。普通窗口 60 帧目标及硬件、分辨率、画质和帧时间标准见本页 1.1 契约；4K60 是素材规格。离线演示不能证明实时性能，手动采集重复帧未稳定修复。
- **发行与权利**：商务权利核验现按用户要求暂缓，保留已有来源且不声称“付费／可下载即已核验商用”。真实渠道及其条款未知，不提前承诺商店审核通过。
- **恢复**：每个通过验证的任务独立提交；资产原件不改写，失败产物留忽略区；必要回退用普通修复或撤销提交，不改写历史。发布候选以版本、提交和文件校验值关联。

最终必须满足：

1. 在已确定的支持系统与目标机器上独立启动、显示中文、完成一个完整农事循环、退出重开并保留状态；没有必须安装的开发软件或访问生成服务的运行依赖。
2. 时间、重复动作、离线、休眠恢复、坏档和保存失败有对应测试；不得重置数据掩盖异常，不得重复发放收益。
3. 全部承诺内容、声音、设置和布置可用，界面不穿透，镜头有可靠返回和取消；首次游玩不是只有等待或空白场景。
4. 两种作物的阶段和正式环境达到确认风格；真实运行主界面的构图、景物层次、质感与界面布局按本页校对表接近用户指定参考，并经并排对比验收。源文件、模型、导入配置和必要来源可在干净工作副本重建。
5. 实际玩法的性能达到已定口径，焦点 LOD 和景深三种观察状态有实测，切换不破坏轮廓、点选和清晰度；严重阻断、崩溃、丢档、无法操作问题清零。非阻断问题如实列出，不靠高配机或离线视频代替证明。
6. 发行包包含必要数据、许可、版本、说明和校验值，移出仓库后验证；本轮通用本地发行材料齐全；没有渠道决定时不承诺任何商店的提交验收或审核结果。
7. 执行者完成真实程序最终试玩并交付用户可试玩包，缺陷已关闭或如实列明；明确用户反馈与签收尚未取得；宣传图来自实际版本，概念图与离线演示明确用途，Tripo 贡献有真实证据。

## 八、跨工具接手与持续更新

1. 开始前依次读总览、本页、当前任务，必要时读前置执行记录；再按任务领域读根 `AGENTS.md` 与相关规则。核对版本、Git 状态和文件，确认计划仍适用，将该任务与总览标为“进行中”。
2. 执行中只处理当前范围。新事实改变步骤／依赖时先改任务文件；方案改变更新本页，跨任务决定更新重要记录。补确切路径与实际命令，不自行重编号，不顺便启动其他任务。
3. 完成后按清单验证，填写实际改动、结果、遗留、偏差、后续影响及提交。通过才标“已完成”；实现完成但证据不足标“待验证”。同步总览数量、阶段、当前任务和倒序最近记录。
4. 阻塞时标“已阻塞”，写原因、解除条件、受影响后续与替代方案；只阻塞相关任务，不把账号、渠道或审美待定扩成全仓暂停。用户已授权整个计划开工，不重复等待逐项授权。
5. 每个任务完成时形成一次独立完整的 Git 提交，包含该任务实际改动与计划更新；归档素材保持忽略。按实际变化维护既有规则和环境文档，保护并行任务改动。
6. 接手不只依赖会话记忆或私有工具；每个子代理生成可入库交接文件。进度只在总览和任务状态同步维护，长期方案在本页，关键决定在重要记录；不再引入看板、日报或重复台账。
