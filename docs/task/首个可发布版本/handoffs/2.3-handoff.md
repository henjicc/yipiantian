- `Game/farm/farm_store.gd`：串行存储边界，`new(directory="user://farm")`、`load_state()`、`save(snapshot)`、`recover()`。所有玩法字段校验复用 `farm_state.restore_snapshot`，未改生长规则。
- `Game/scenes/main.gd`：启动先读档；真正缺档才创建六田初始状态。动作成功即保存；每 30 秒、失去焦点和正常关闭保存；每秒及重新获得焦点只调用同一 UTC 结算入口。失败锁住农事输入，重试只保存当前快照，关闭失败窗口保留；明确点击“仍然退出（最新进度未保存）”才放弃内存进度。
- `farm_hud.gd`：`HUD/Layout/StorageOverlay` 中 `Retry`、`Recover`、`Exit` 与状态文案；独立信号交给 main，不自行读写。未读成功时隐藏田块，避免把初始化画面误当玩家档。
- 旧 `prototype_smoke`、`farm_interaction_test`、`recording_controls_smoke` 均在入树前注入独立 Store，不能再写玩家档。
- `scripts/record.ps1 -FarmDemo -Seconds 28` 与 `Game/development/recording_session.gd`：独立录制存档、明确的 UTC 1440 秒演示推进；正常游戏速度不变。`export_presets.cfg` 排除 `development/*`，发行程序在读玩家档之前拒绝 `--record-session`。

## 格式、实际位置与恢复语义

当前格式严格为 `{ "version": 1, "farm": { "fields": {...}, "harvested": {...} } }`；字段保存稳定田块 ID、作物 ID、累计生长秒、是否浇水、UTC `last_settled`，不保存节点和推导阶段。最大 64 KiB，完整解析、有限数值与玩法结构校验后才接受。

Windows 默认实际目录：`%APPDATA%/Godot/app_userdata/我有一片田/farm/`。

外部契约核验采用 Godot 官方 [FileAccess](https://docs.godotengine.org/en/stable/classes/class_fileaccess.html) 的 flush/错误边界及 [DirAccess](https://docs.godotengine.org/en/stable/classes/class_diraccess.html) 的 rename/链接说明；现机固定 4.7.2 行为再用隔离 Windows 文件实验确认，没有仅凭文档声称断电安全。

1. `farm.json` 为主档；新快照写入 `farm.pending.json`，flush 后重读验证。
2. 当前有效主档先复制到 `farm.backup.pending.json`，验证后替换 `farm.backup.json`，最后以 rename 替换主档；不预删主档。Windows 已存在目标可替换、只读目标失败仍保留旧字节均经实测。
3. 主档坏、有效备份存在时只提供显式恢复；恢复先保留 `farm.unreadable.<pid>.<ticks>.json` 并核对哈希。主备都坏、不能读取、未知版本均锁住，不能静默重建。
4. 只有从未有过主档和备份的首次写入中断可以提供 pending 恢复；已有有效主档始终优先，不能重放未提交动作。保留上份备份意味着恢复可能丢失最近进度，界面明确说明。
5. 读档后若磁盘主档变动，拒绝旧实例覆盖。此处是单游戏实例的同步写入和陈旧快照保护，并未宣称跨进程数据库事务或断电硬件级 fsync 保证。

后续解锁、布置和设置应放在外壳相应字段，保持 farm 的状态所有权；增加字段必须升级版本并实现明确的 v1→新版本转换、完整校验和隔离测试。不能仅移除 `data.size()` 检查而默默丢弃未知数据；较新版本始终拒绝覆盖。3.3 的视觉替换不应改变田块 ID 或依赖模型推算保存状态。
