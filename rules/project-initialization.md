# 项目初始化与规则适配

> 读取时机：状态为 `pending`、状态异常、用户要求重新初始化或整体维护模板时。

## 触发与例外

- 状态唯一存放在 [`project-context.md`](project-context.md) 顶部。`pending` 要求主动完成下述适配，不能跳过并直接开展业务实现。
- 当前请求是维护初始化模板本身时，只优化可复用规则，保留 `pending` 及必要栏目；不得填入模板仓库的路径、分支等作为未来业务项目事实。
- 只读请求仅调查、说明所需适配，不写状态或规则。此例外结束后，下一次获准实施的任务仍按实际状态判断。
- 初始化授权只覆盖项目内规则适配，不自动授权业务实现、安装依赖、初始化 Git、付费、外部写入或部署。用户同时请求业务实现时，适配完成后继续原任务。
- 用户明确要求重新初始化业务项目时，保留已有有效事实，将状态设为 `pending` 后重新核对适用范围；不要清空用户约定。

## 调查与适配

1. 检查已有代码、配置、测试、Git 状态和项目约定，区分模板栏目、现行事实与用户内容。按当前阶段确认目标、产品形态、运行边界和验证入口；不要因目录为空猜造技术栈。
2. 自行确认可调查事实；剩余问题只有会改变范围、平台、架构或安全决定时才询问。使用可用的交互式提问工具集中问最少问题，工具不适用时简短询问；继续不依赖答案的调查。
3. 按真实项目重写上下文，优先引用实际配置和脚本，仅补充不易推断的约束。新项目尚无代码或命令时如实说明，以已确认的当前阶段方案作为依据，不把计划写成已实现。
4. 审查全部规则与路由：删除不适用的模板段落，合并重复约束，保留用户特有约定。以当前实现及已批准建设范围判断适用性，不能因尚未实现就删除计划所需规则；确无 UI 时删除 UI 规则及路由，无远端服务不虚构后端，无长期服务删除服务栏目。
5. 删除规则文件时同步处理所有入链；保留状态检查、初始化入口及主动维护机制。不能确认归属或会丢失用户约定时保留内容，先解决实质冲突。

## 完成与恢复

仅当以下条件全部满足，才最后将 `template_state` 改为 `ready`：

- 当前阶段的产品目标、范围、运行形态和关键边界已明确，没有阻塞后续工作的必要决定。
- 上下文只保留已核验事实及明确标注的已批准计划；没有无意义占位、猜造路径或命令。
- 路由、链接和规则适用范围一致；无相互冲突或已失效的约束。
- 已确认当前阶段的实际验证方式，以及适用的环境、数据和权限限制。

按 [`testing.md`](testing.md) 完成规则验证；Git 提交和同步按 [`git-workflow.md`](git-workflow.md) 处理。`ready` 表示本地项目约定已适配，不表示业务功能、测试或远端同步已完成。

- 中断或缺少关键决定时保持 `pending`，在上下文记录最少必要的待解决事项；恢复时核对已完成内容，只继续剩余部分。
- 上下文文件或状态缺失、状态非法时，先保护已有内容并调查；符合完成条件则恢复为 `ready`，否则补建必要上下文、记录缺口并设为 `pending`。只读任务不得修复状态。
- `ready` 后普通事实变化按维护规则增量更新；若内容证明初始化关键条件实际未满足，按上述恢复流程处理，不因小改动重做初始化。
